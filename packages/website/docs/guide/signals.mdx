# Signals

Signals are the primary reactivity model in AngularLynx. Since the Lynx runtime does not support Zone.js, signals provide the explicit reactivity that Angular needs to know when to re-render components.

Angular's full signals API — `signal()`, `computed()`, `effect()`, `input()`, `output()`, `toSignal()`, and `toObservable()` — all work in AngularLynx exactly as documented on [angular.dev](https://angular.dev/guide/signals).

This page covers the Lynx-specific differences you need to know.

## Why Signals Are Required

In web Angular with Zone.js, change detection runs automatically after every async operation. In AngularLynx, **there is no Zone.js**, so Angular needs explicit signals to know when state has changed.

- **Fine-grained updates** — Only components that read a changed signal are re-checked
- **Works with zoneless CD** — Signal changes automatically schedule change detection
- **Batched rendering** — All signal changes within a macrotask are committed together via `__FlushElementTree()`

## Lynx-Specific Considerations

### All updates are batched

Because Lynx flushes element changes atomically via `__FlushElementTree()`, multiple signal updates within the same synchronous context are always applied together:

```typescript
onSubmit(): void {
  this.loading.set(true);
  this.error.set('');
  this.data.set(newData);
  // All three changes appear on screen simultaneously after the next flush
}
```
